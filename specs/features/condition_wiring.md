# Spec: Condition Wiring Through Builder (WHEN Clauses)

> **Status:** Implemented
> **Created:** 2026-02-17
> **Completed:** 2026-02-18
> **Spec type:** Feature

---

## Purpose

The `Condition` dataclass (L1), `ConditionOp` enum (L1), `_CONDITION_PROPS` schema (L2), and `WHEN` relationship constraint (L2) all exist, but conditions are architecturally misplaced and disconnected: the builder creates Condition nodes inside the schema subgraph (where they have zero relationships), never creates WHEN edges to connect them to MappingRules, and the summarizer never surfaces condition information in processing instructions. Agents building recipes with conditional mapping logic (overtime rules, tax brackets, categorical routing by employee type or department) get no condition guidance when processing data.

This spec moves conditions to where they belong (the recipe subgraph), wires WHEN relationships with proper functional composition, adds a real validator for WHEN targets, and surfaces conditions in processing instructions.

---

## Layer Placement

**Primary layer:** L5 — MCP Server (builder + summarizer)
**Layers touched:**

| Layer | Package | What changes |
|-------|---------|--------------|
| L1 Types | `domain/types_recipe.py` | Nothing — `Condition`, `ConditionOp` already exist |
| L2 Ontology | `domain/ontology_recipe.py` | Nothing — `_CONDITION_PROPS` and `WHEN` constraint already exist |
| L3 Logic | `domain/logic.py` | Remove `condition_nodes` from `build_source_schema_pattern`; add `extract_conditions_for_rule`; add `validate_when_targets` |
| L4 Persistence | `persistence/` | Nothing — properties and relationships serialize automatically |
| L5 MCP Server | `mcp_server/builders.py`, `mcp_server/summarizers.py` | Move condition building to recipe subgraph, create WHEN rels, emit conditions in instructions |

## Design Decisions

### 1. Conditions belong in the recipe, not the schema

A SourceSchema describes the structure of the input file — column names, data types, positions. Conditions control when mapping rules fire — "WHEN employee_type EQUALS salaried." Every other node in the schema subgraph connects to the schema node (Column via HAS_COLUMN, Measure via HAS_MEASURE). Conditions connect to MappingRules via WHEN — they are mapping logic, not source structure.

**Current (wrong):** `schema.conditions[]` → condition nodes float in the schema subgraph with zero relationships.

**After:** `recipe.conditions[]` → condition nodes built in the recipe subgraph, connected via WHEN rels in the same builder call.

### 2. WHEN relationships are the only supported mechanism

`MappingRule` has `condition_operator` and `condition_value` fields in L1, but no `column` field. An inline condition without a column reference cannot be evaluated. Rather than add a field to a frozen dataclass (L1 change), this spec makes WHEN relationships the documented path. The inline fields remain in L1 as-is but are not wired through the builder.

### 3. No cross-subgraph ID regeneration

The existing code passes explicit node references between builders (e.g., `schema_node.id` is passed to `_build_recipe_nodes`). This spec follows that pattern: condition node IDs are built once and used directly — never regenerated by convention.

### 4. A real validator, not an assumed one

`validate_pipeline_connectivity` only checks TRANSFORMS edges. This spec adds `validate_when_targets` to verify WHEN edges point to nodes that exist in the pattern.

## Domain Types (L1)

No Layer 1 changes required. All types already exist:

```python
# domain/types_recipe.py
class ConditionOp(Enum):
    EQUALS = "equals"              # Categorical: WHEN department EQUALS "engineering"
    NOT_EQUALS = "not_equals"      # Categorical: WHEN pay_type NOT_EQUALS "exempt"
    GREATER_THAN = "greater_than"  # Numeric: WHEN hours GREATER_THAN "40"
    LESS_THAN = "less_than"        # Numeric: WHEN gross_pay LESS_THAN "1000"
    IS_NULL = "is_null"            # Missing: WHEN bonus IS_NULL
    IS_NOT_NULL = "is_not_null"    # Present: WHEN commission IS_NOT_NULL
    ALWAYS = "always"              # Default: rule always fires

@dataclass(frozen=True)
class Condition:
    recipe_id: str
    condition_id: str
    column: str              # Source column to evaluate
    operator: ConditionOp    # Comparison operator
    value: Optional[str] = None  # Comparison value (None for IS_NULL/IS_NOT_NULL/ALWAYS)
```

### Categorical Data Support

`ConditionOp.EQUALS` and `ConditionOp.NOT_EQUALS` handle categorical matching natively. The `Condition.value` field is `Optional[str]`, so all comparisons are string-based — categorical columns (employee_type, department, pay_type) work directly:

| Use Case | Column | Operator | Value |
|----------|--------|----------|-------|
| Route by employee type | `employee_type` | `equals` | `"salaried"` |
| Exclude admin department | `department` | `not_equals` | `"admin"` |
| Overtime threshold | `hours_worked` | `greater_than` | `"40"` |
| Handle missing bonus | `bonus_amount` | `is_null` | (none) |
| Commission-eligible only | `commission_rate` | `is_not_null` | (none) |

```python
    schema_node: Node,
    column_nodes: List[Node],
    measure_nodes: List[Node],
    column_rels: List[Relationship],
    measure_rels: List[Relationship],
    aggregates_rels: List[Relationship] | None = None,

        relationships.extend(aggregates_rels)
```

### New: `extract_conditions_for_rule`

```python
def extract_conditions_for_rule(
    pattern: GraphPattern,
    rule_node_id: str,
) -> Tuple[Node, ...]:
    """Extract Condition nodes connected to a MappingRule via WHEN.

    Follows outgoing WHEN edges from the rule node and returns the
    target Condition nodes. Returns empty tuple if no WHEN edges exist.
    """
    condition_ids = {
        rel.end_node_id
        for rel in pattern.relationships
        if (
            rel.type == RelationshipType.WHEN
            and rel.start_node_id == rule_node_id
        )
    }
    return tuple(
        n for n in pattern.nodes
        if n.id in condition_ids and NodeLabel.CONDITION in n.labels
    )
```

Follows the exact pattern of `extract_debit_credit_slots` and `extract_measures_for_schema`.

### New: `validate_when_targets`

```python
def validate_when_targets(pattern: GraphPattern) -> ValidationResult:
    """Verify every WHEN relationship targets a Condition node in the pattern.

    Hard block — a dangling WHEN edge means a rule references a condition
    that doesn't exist, which would silently skip conditional logic.
    """
    node_ids = {n.id for n in pattern.nodes}
    errors: list[str] = []

    for rel in pattern.relationships:
        if rel.type == RelationshipType.WHEN:
            if rel.end_node_id not in node_ids:
                errors.append(
                    f"WHEN target '{rel.end_node_id}' from rule "
                    f"'{rel.start_node_id}' not found in pattern"
                )

    if errors:
        return ValidationResult.failure(tuple(errors))
    return ValidationResult.success()
```

Follows the exact pattern of `validate_pipeline_connectivity`.

### Changed: `validate_recipe`

Add `validate_when_targets` to the orchestrated validators:


### Builder changes (`mcp_server/builders.py`)

#### Change 1: Remove conditions from `_build_schema_nodes`

```python
# Before (returns 5 values):

# After (returns 4 values):

```

#### Change 2: Add condition building + WHEN rels to `_build_recipe_nodes`

Conditions are defined in `recipe.conditions[]` and built alongside rules. The WHEN rels reference condition node IDs directly — no regeneration needed because conditions and rules are built in the same function.

```python
def _build_recipe_nodes(
    recipe_spec: Dict[str, Any],
    schema_node_id: str,
    recipe_id: str,
) -> Tuple[Node, List[Node], List[Node], List[Node], List[Node], List[Node], List[Relationship]]:
    """Build AccountingRecipe + MappingRule + AccountSlot + Account + Reference + Condition nodes and all rels.

    Returns: (recipe_node, rule_nodes, slot_nodes, account_nodes, reference_nodes, condition_nodes, relationships)
    """
    ...

    # Build conditions — condition_id → node_id map for WHEN edges
    condition_nodes: List[Node] = []
    condition_id_map: Dict[str, str] = {}  # condition_id → node_id
    for cond_spec in recipe_spec.get("conditions", []):
        cond_node_id = _generate_node_id(recipe_id, "cond", cond_spec["condition_id"])
        cond_props: Dict[str, Any] = {
            "recipe_id": recipe_id,
            "condition_id": cond_spec["condition_id"],
            "column": cond_spec["column"],
            "operator": cond_spec["operator"],
        }
        if cond_spec.get("value") is not None:
            cond_props["value"] = cond_spec["value"]
        condition_nodes.append(Node(
            id=cond_node_id, labels={NodeLabel.CONDITION}, properties=cond_props,
        ))
        condition_id_map[cond_spec["condition_id"]] = cond_node_id

    for rule_spec in recipe_spec.get("rules", []):
        ...  # existing rule building

        # WHEN: rule → condition (using the map, not regenerated IDs)
        when_ref = rule_spec.get("when")
        if when_ref:
            cond_target = condition_id_map.get(when_ref)
            if cond_target:
                relationships.append(Relationship(
                    id=_generate_node_id(recipe_id, "rel_when", f"{rule_spec['rule_name']}_{when_ref}"),
                    type=RelationshipType.WHEN,
                    start_node_id=rule_id,
                    end_node_id=cond_target,
                    properties={},
                ))
            # If when_ref not in map, the WHEN rel is omitted here.
            # validate_when_targets catches dangling refs at Gate 1.

    ...
    return recipe_node, rule_nodes, slot_nodes, account_nodes, reference_nodes, condition_nodes, relationships
```

Key: `condition_id_map` is built from the conditions in this same function. WHEN rels look up actual node IDs from the map — no cross-subgraph coupling, no ID regeneration.

If `when_ref` doesn't match any condition in the map, the relationship is not created. If the user also misspelled the condition_id, there's simply no WHEN edge. The `validate_when_targets` Gate 1 validator does NOT catch this case (there's no dangling edge — there's just no edge). This is acceptable because an unconditional rule is the safe default. A future enhancement could warn when a `when` field doesn't match any condition_id.

#### Change 3: Update `build_pipeline_from_spec`

```python
def build_pipeline_from_spec(spec: Dict[str, Any]) -> GraphPattern:
    recipe_id = spec["recipe_id"]

    # 1. Build schema subgraph (no conditions)
    schema_spec = spec["schema"]
    schema_node, col_nodes, msr_nodes, schema_rels = _build_schema_nodes(
        schema_spec, recipe_id,
    )
    ...
    schema_pattern = build_source_schema_pattern(
        schema_node=schema_node,
        column_nodes=col_nodes,
        measure_nodes=msr_nodes,
        column_rels=col_rels,
        measure_rels=msr_rels,
        aggregates_rels=agg_rels if agg_rels else None,
    )

    # 2. Build recipe subgraph (conditions + WHEN rels live here)
    recipe_spec = spec["recipe"]

    # Backward compat: move schema.conditions to recipe.conditions
    if "conditions" in schema_spec and "conditions" not in recipe_spec:
        recipe_spec = dict(recipe_spec, conditions=schema_spec["conditions"])

    recipe_node, rule_nodes, slot_nodes, account_nodes, ref_nodes, cond_nodes, recipe_rels = _build_recipe_nodes(
        recipe_spec, schema_node.id, recipe_id,
    )

    ...
    additional_nodes = account_nodes + ref_nodes + cond_nodes
    ...
```

Condition nodes flow through `additional_nodes` into `build_recipe_pattern`, following the same pattern used for Account nodes and Reference nodes. WHEN rels are already in `recipe_rels`.

## Data Flow

```
JSON spec (conditions in recipe.conditions[], "when" refs in rules)
    |
    v
builders.py build_pipeline_from_spec()
    |  Backward compat: schema.conditions → recipe.conditions
    v
builders.py _build_schema_nodes()        builders.py _build_recipe_nodes()
    |  Returns: schema, cols, msrs,          |  Builds: conditions, rules, slots,
    |  rels (NO conditions)                  |  accounts, refs, WHEN rels
    |                                        |
    |  condition_id_map built from           |
    |  recipe.conditions[]                   |
    |                                        |
    |  WHEN rels use map for target IDs      |
    |  (no cross-subgraph coupling)          |
    v                                        v
build_source_schema_pattern()          build_recipe_pattern()
    |  (no condition_nodes param)            |  condition_nodes via additional_nodes
    v                                        |  WHEN rels in recipe_rels
    |                                        v
    └──────────────┬─────────────────────────┘
                   v
    compose_pipeline_pattern(schema, recipe)
                   |
                   v
    Gate 1: validate_recipe() includes validate_when_targets()
                   |  Checks: every WHEN rel targets a node in the pattern
                   v
    Neo4j: MERGE nodes + MERGE WHEN relationships
                   |
                   v
    load_recipe → cached GraphPattern with Condition nodes + WHEN rels
                   |
                   v
    summarizers.py summarize_processing_instructions()
        |  extract_conditions_for_rule(pattern, rule.id) → follow WHEN edges
        v
    JSON response: rules[].conditions = [{column, operator, value}]
```

```json
  "rules": [
    {"name": "gross_pay", "source_measure": "total_gross_pay", ...}
  ]
}
```

### Happy path: shared condition (two rules, one condition)

```json
// Input — same condition referenced by multiple rules
{
  "recipe": {
    "conditions": [
      {"condition_id": "is_salaried", "column": "employee_type", "operator": "equals", "value": "salaried"}
    ],
    "rules": [
      {"rule_name": "salary_expense", "when": "is_salaried", ...},
      {"rule_name": "benefits_expense", "when": "is_salaried", ...}
    ]
  }
}

// Graph: two WHEN edges, one Condition node
// (salary_expense) -[:WHEN]-> (is_salaried)
// (benefits_expense) -[:WHEN]-> (is_salaried)
```

### Edge case: "when" references undefined condition_id

```json
// Input — "when" doesn't match any condition in recipe.conditions
{
  "recipe": {
    "conditions": [],
    "rules": [
      {"rule_name": "bad_rule", "when": "nonexistent", ...}

// Behavior: condition_id_map has no entry for "nonexistent".
```

## Invariants

### Graph semantics
- Condition nodes are in the recipe subgraph, connected to MappingRules via WHEN
- A MappingRule MAY have zero, one, or many WHEN relationships to Condition nodes
- Multiple WHEN conditions on a single rule are AND-joined (all must be true)
- A single Condition node MAY be referenced by multiple MappingRules (shared conditions)
- WHEN relationships are one-directional: MappingRule → Condition
- Condition nodes have all required fields: `recipe_id`, `condition_id`, `column`, `operator`

### Functional constraints
- `_build_recipe_nodes` builds conditions and WHEN rels in the same function — no cross-subgraph coupling
- `condition_id_map` uses actual node IDs, not regenerated conventions
- `build_source_schema_pattern` no longer accepts condition_nodes — conditions never float disconnected
- `extract_conditions_for_rule` is a pure function following the `extract_debit_credit_slots` pattern
- `validate_when_targets` is a pure function following the `validate_pipeline_connectivity` pattern
- Backward compatibility: `schema.conditions[]` migrated to `recipe.conditions[]` by the caller

### Layer boundaries
- domain/ is not modified at L1 or L2
- L3 signature change to `build_source_schema_pattern` (remove `condition_nodes`)
- New L3 functions: `extract_conditions_for_rule`, `validate_when_targets`
- New L5 import in summarizers.py: `extract_conditions_for_rule` from `domain.logic`
- Pure functions (builders, summarizers) do not import from persistence/

## Out of Scope

- **Completing inline conditions**: `MappingRule.condition_operator`/`condition_value` exist in L1 but lack a `column` field. Adding `condition_column` to MappingRule's PropertySchema is an L1+L2 change. If needed, spec separately.
- **IN / NOT_IN operators**: Matching a column against a set of values (e.g., `department IN ["engineering", "product"]`) requires new `ConditionOp` members at L1. Useful for multi-category routing but separate from wiring existing operators.
- **Compound conditions (OR logic)**: Multiple WHEN edges on one rule are AND-joined. OR logic would need a grouping mechanism. Defer until a real use case demands it.
- **Warning for unmatched "when" references**: If `when: "typo"` doesn't match any `condition_id`, no WHEN edge is created and the rule fires unconditionally. A soft warning could catch this, but it's not a correctness issue — the safe default is unconditional.
- **Condition-to-Reference lookup**: `Condition` can USES_REFERENCE a Reference node (constraint exists). Wiring this for lookup-table conditions is a separate spec — see Knowledge Zone Reference Data spec.
- **Column name validation**: Verifying that `Condition.column` matches a column in the schema. Useful Gate 1 validator but separate from wiring conditions through the builder.

## Open Questions

- [x] **Should multiple WHEN conditions be AND or OR?** **Decision: AND.** Multiple WHEN edges on a single rule are AND-joined — all must be true. This matches common accounting patterns. OR logic deferred until a real use case demands it; a `condition_logic: "or"` property on MappingRule is the likely extension point.
- [x] **Should unmatched "when" references produce a soft warning?** **Decision: silently ignored for now.** If a `when` value doesn't match any `condition_id` in the map, no WHEN edge is created and the rule fires unconditionally (safe default). A `validate_condition_references` soft-warning validator is captured in Out of Scope for a future spec.
